# Workflow 저작의 캐시 재사용을 공급자별로 고치고 놓친 이유를 기록함

## 0. 한눈에

| | |
|---|---|
| 요청 | Workflow 저작 호출의 캐시 재사용이 낮은 이유를 찾아 공급자별로 고치고, 놓친 호출은 이유를 알 수 있게 기록 |
| 결론 | legacy Codex 백엔드는 앞 요청 입력의 끝 근처까지 같은 요청에만 캐시를 다시 써서, 분석 뒤 초안은 매번 출처를 다시 읽었습니다. 출처만 담은 예열 요청과 초안 지시문 수정으로 같은 원고의 캐시 비율이 31%에서 60%로, 정가가 $0.50에서 $0.40으로 바뀌었습니다. |
| 믿을 수 있는 정도 | PC74에서 쓸 수 있는 로그인은 legacy Codex 하나였습니다. 캐시 규칙은 짧은 시험 호출 40회로 반복 확인했습니다. 저작 전체는 방식마다 한 번씩 돌렸습니다. Anthropic, OpenAI API 키, "Sign in with ChatGPT"는 실제 호출 없이 GAID가 보내는 요청 본문만 확인했습니다. |
| 결정할 일 | 없음 |

## 1. 요청한 것

> gaid-authoring-tokens과 관련하여 질문이다. GAID 시스템에서는 왜 캐시를 읽지 못하나? 입력토큰은 덜써서 좋지만 캐시 재사용율이 너무 낮다. PI특성 때문인지 수정이 가능한지 답변만 해줘.

> 해당 문제를 oracle search로 검색해서 조사하자. 정말 1, 2번만 수행하면 되는지 확인하고 싶다.

> 작업하자. — 2026-10-24 요청

완료 기준(조사에서 권한 순서를 그대로 받은 것):

1. 호출마다 경로, 인증 방식, 사용량(캐시 읽기·쓰기 포함), 시각을 기록합니다.
2. 출처 끝에 캐시 경계를 둡니다.
3. 공급자별 보존 정책을 정합니다.
4. 수정 호출에서 이전 응답을 보내는 두 방식을 비교합니다.
5. 첫 초안 통과율을 올립니다.
6. 같은 원고·같은 답으로 다시 재서 전후를 비교합니다.
7. 점검을 통과하고 보고서를 씁니다.

## 2. 수행한 것

1. 조사 결과의 핵심 주장을 GAID에 설치된 Pi 1.0.0 소스와 대조했습니다. 구독 로그인 두 경로는 캐시 보존 옵션을 보내지 않습니다. Anthropic에는 Pi가 이미 캐시 표식을 붙입니다. 시도 기록이 캐시 읽기를 빠뜨립니다. 세 주장 모두 맞았습니다.
2. legacy Codex 로그인으로 짧은 시험 호출을 보내 어떤 요청 모양에서 캐시가 다시 쓰이는지 쟀습니다. 시험마다 지시문 맨 앞에 고유 표식을 붙여 시험끼리 캐시가 섞이지 않게 했습니다.
3. 출처를 독립된 블록으로 나눴고, 경로별 경계·보존 정책과 호출 기록을 넣었습니다. legacy Codex에는 예열 요청을 넣었습니다. 초안 지시문에는 과거 실패의 대부분을 차지한 세 규칙을 적었습니다.
4. 지난 측정과 같은 원고·같은 답으로 GAID 저작을 두 번 다시 돌렸습니다. 첫 번째는 예열 없이, 두 번째는 예열을 넣고 돌렸습니다.

### 3.1 분석 뒤 초안이 캐시를 놓친 이유

재측정 1의 새 기록에서는 분석과 초안이 지시문 830토큰, 출처 24,017토큰까지 토큰 단위로 같았습니다. 같은 캐시 키로, 분석 응답이 끝나고 8초 뒤에 초안을 보냈습니다. 그래도 초안은 캐시를 읽지 못했습니다. 지난 보고서의 "맞을 때도 안 맞을 때도 있다"는 설명은 틀렸습니다. 이 실패는 매번 재현됩니다.

표 3. 첫 요청의 출처 뒤 꼬리 길이에 따른 두 번째 요청의 캐시 읽기 (시험 호출)

| 첫 요청에서 출처 뒤에 붙은 것 | 두 번째 요청의 캐시 읽기 |
|---|---:|
| 짧은 지시 (약 30토큰) | 24,704 |
| 같은 짧은 지시, 2분 30초짜리 긴 응답 | 24,704 |
| 같은 짧은 지시, 270초·330초·10분·20분 뒤 | 24,704 |
| 같은 짧은 지시 뒤, 두 번째 요청에 초안 크기 지시(약 1만 토큰) | 24,704 |
| 꼬리 약 400·1,200·2,200·5,000토큰 | 0 |
| 실제 분석 지시 (1,044토큰) | 0 |

legacy Codex 백엔드는 각 요청 입력의 끝에만 캐시를 남깁니다. 다음 요청은 그 끝에서 몇십 토큰 안에서 갈라질 때만 앞부분을 다시 씁니다. 분석 요청은 출처 뒤에 1,044토큰짜리 분석 지시가 붙어 있습니다. 출처만 같은 다음 작업(초안, 개정)은 이 캐시를 쓰지 못합니다. 수정 호출은 앞 요청을 그대로 이어 붙이므로 캐시가 맞았습니다.

이 백엔드는 출처 끝에 경계를 직접 표시하는 기능도 "이 모델은 지원하지 않는다"는 오류로 거부했습니다. 남은 방법은 출처 끝에서 끝나는 요청을 한 번 보내는 것입니다. GAID는 이 경로에서 작업의 첫 호출 전에 "출처 + 빈 JSON을 답하라는 한 줄" 예열 요청을 보냅니다. 같은 저작 프로젝트에서 20분 안에 예열한 적이 있으면 다시 보내지 않습니다. 20분은 시험에서 캐시가 살아 있던 가장 긴 간격이고, 더 긴 간격은 재지 않았습니다.

예열 한 번에는 출처 한 벌을 캐시 없이 읽는 비용이 듭니다(정가 $0.05). 바로 이어지는 호출이 같은 양을 캐시로 읽으므로 첫 작업에서는 비용이 거의 그대로이고, 20분 안에 오는 다음 작업부터 출처 한 벌씩 아낍니다.

### 3.2 공급자별 경계와 보존

| 경로 | 출처 끝 경계 | 보존 | 확인 방법 |
|---|---|---|---|
| OpenAI API 키 (GPT-5.6 이후 모델) | 출처 블록에 명시 경계 | 기본 30분 | 최종 요청 본문 (실제 호출 없음) |
| OpenAI API 키 (이전 모델) | 없음 | 24시간 (쓰기 할증 없음) | 정책만, 시험 없음 |
| Sign in with ChatGPT | 없음 | 보내지 않음 (Pi가 지원하지 않는 항목으로 보고 뺌) | 최종 요청 본문 (로그인 만료) |
| OpenAI Codex (legacy) | 거부됨 → 예열 요청 | 보내지 않음 | 실제 호출 |
| Anthropic (키 또는 구독) | 출처 블록에 캐시 표식 (표식 4개 한도 안) | 5분. 직전 호출과의 간격이 5분을 넘으면 출처까지 1시간 | 최종 요청 본문 (실제 호출 없음) |
| 그 밖 (OpenRouter, 기관 vLLM, MiniMax, Ollama) | 없음 | 공급자 기본값 | 바꾸지 않음 |

Anthropic의 1시간 보존은 쓰기 단가가 입력의 2배입니다(5분은 1.25배). 캐시를 읽으면 남은 시간이 다시 늘어납니다. PC74에 남은 저작 시도 220건에서 호출 하나는 중앙값 243초가 걸렸고, 72건은 5분을 넘었습니다. 다음 호출이 5분 넘게 지나 오는 일이 흔합니다. GAID는 직전 간격이 5분을 넘었을 때만 1시간을 고릅니다. 출처 뒤의 바뀌는 꼬리는 5분으로 둡니다.

### 3.3 수정 호출에서 이전 응답을 보내는 방식

표 4. 긴 응답(9,498토큰) 뒤의 같은 수정 요청 (시험 호출, legacy Codex)

| 방식 | 캐시 안 된 입력 | 캐시 읽기 | 출력 | 시간 |
|---|---:|---:|---:|---:|
| 모델의 원래 응답을 그대로 이어 보냄 | 233 | 34,176 | 8,597 | 81초 |
| 이전 응답을 글로 접어 사용자 메시지에 붙임 (지금까지 방식) | 8,714 | 24,704 | 8,745 | 81초 |

legacy Codex에서 원래 응답을 그대로 이어 보내면 서버가 앞 요청과 응답을 이어 써서 이전 응답을 다시 보내지 않습니다. 그래서 이 경로의 수정 호출만 원래 응답을 이어 보냅니다. 다른 경로는 어느 방식이든 이전 응답을 다시 보내야 하고, 이어 보내기는 추론 기록까지 더하므로 지금 방식을 유지합니다. 두 재측정 모두 초안이 첫 응답에서 통과해 실제 수정 호출이 없었으므로, 두 방식의 품질 차이는 재지 못했습니다.

### 3.4 첫 초안 통과율

PC74의 저작 기록 가운데 최근 지시문 판(10-22 이후)의 초안·개정 시도는 23건이었습니다. 이 중 8건이 첫 응답에서 통과했습니다. 실패 15건 중 13건에는 세 가지 오류만 있었습니다.

1. 이미 답한 선택을 선택지 하나로 남김
2. 시작 설정의 키에 선택 대신 질문 이름을 씀
3. Workflow에 필요한 방법 판단 항목이 빠짐

초안 지시문에 이 세 규칙을 적었고, 서버 검사는 바꾸지 않았습니다. 두 재측정의 초안은 모두 첫 응답에서 검사 오류 없이 통과했습니다. 지난 두 실행은 모두 수정 호출이 필요했습니다. 실행이 두 번뿐이라 통과율을 숫자로 말할 수는 없습니다.

| 완료 기준 | 결과 | 근거 |
|---|---|---|
| 1. 호출 기록, 원장의 캐시 쓰기, 시도 기록의 캐시 읽기 누락 수정 | 충족 | 3.1의 원인을 이 기록으로 찾음 |
| 2. 출처 블록 분리와 출처 끝 경계, 최종 요청 본문 확인 | 충족 (legacy Codex는 실제 호출, 나머지는 요청 본문만) | 3.2 |
| 3. 공급자별 보존 정책과 문서화 | 충족 | 3.2, 설계 문서 |
| 4. 수정 호출 방식 비교, 나은 경우만 채택 | 비용은 비교해 legacy Codex에만 채택. 품질은 실제 수정 호출이 없어 미확인 | 표 4 |
| 5. 첫 초안 통과율 개선 (검사 완화 없음) | 지시문 수정. 재측정 2회 모두 첫 응답 통과 | 3.4 |
| 6. 같은 원고·같은 답으로 전후 비교, 남은 실패 설명 | 충족 (legacy Codex만) | 표 1, 3.1 |
| 7. 점검 통과, 보고서 | 충족 (부하로 실패한 웹 시험 4개 파일은 다시 돌려 통과) | 부록 A |

## 4. 검증

- 과학적 검증: 해당 없음. 비용과 캐시를 쟀고, 초안의 방법 내용이 옳은지는 보지 않았습니다. 네 실행의 초안은 모두 서버 검사를 통과했습니다. 단계는 모두 5개이고, 경고는 환경 패키지 설치 안내 1~2건입니다.
- 비교 기준과 단위: 같은 원고, 같은 답, 같은 모델·추론 수준·로그인으로 쟀습니다. 토큰은 공급자가 보고한 값입니다. 공급자 응답에는 블록별 토큰 내역이 들어 있어, 두 요청의 출처가 같은 토큰 수인지 직접 확인했습니다.
- 반복과 흔들림: 저작 전체는 방식마다 한 번입니다. 출력 토큰은 실행마다 흔들립니다(분석 11,074~15,213, 초안 18,545~22,776). 캐시 안 된 입력의 차이(60,961 → 33,865)는 출처 한 벌(약 2만 5천 토큰)에 가까운 크기이고, 출력이 흔들려도 바뀌지 않습니다. 캐시 규칙은 시험 호출로 반복 확인했습니다. 첫 요청의 꼬리가 짧을 때 다음 요청은 13번 모두 맞았습니다. 꼬리가 400토큰 이상일 때는 시험 5번과 실제 저작 2번이 모두 놓쳤습니다.
- 다른 설명: 재측정 2의 분석 호출은 36분 전 재측정 1의 같은 분석 요청이 남긴 캐시도 읽었습니다. 같은 원고, 같은 프로젝트 이름이라 요청이 같았기 때문입니다. 그래서 캐시 읽기가 예열만으로 얻을 값보다 1,024토큰 많습니다. 이를 빼면 캐시 비율은 59%, 정가 차이는 $0.002입니다. 초안의 캐시 읽기는 예열에서만 올 수 있습니다. 재측정 1의 초안 캐시는 초안 끝에 남아 있어 표 3의 규칙상 쓸 수 없습니다.
- 소프트웨어 검증: 저작 시험은 82개 중 81개가 통과했습니다. 나머지 1개는 시스템 부하 65에서 시간 초과로 실패한 데이터 파일 시험이고, 단독 실행에서는 통과했습니다. 새 시험은 Pi의 실제 OpenAI·Codex·Anthropic 변환을 거친 요청 본문에서 경계 위치, 표식 수, 보존 시간 순서를 확인합니다. 예열이 첫 호출에만 한 번 가는지도 확인합니다. 전체 점검 결과는 부록 A에 적었습니다.

## 5. 한계

- PC74에서 연결된 모델 로그인은 legacy Codex 하나였습니다. "Sign in with ChatGPT"는 만료되었고, Anthropic 로그인과 API 키는 없습니다. 이 경로들은 실제 응답의 캐시 값을 재지 않았습니다.
- "Sign in with ChatGPT"도 legacy Codex와 같은 캐시 규칙일 수 있습니다. 확인하지 못해 예열을 켜지 않았습니다.
- legacy Codex 캐시가 20분보다 오래 사는지는 재지 않았습니다. 연구자가 질문에 20분 넘게 답하면 초안 전에 예열을 다시 보냅니다. 그 경우 아끼는 양은 없고, 비용은 그대로입니다.
- 구독 사용량 한도에서 캐시 입력을 어떻게 세는지는 공개되지 않았습니다. 정가는 크기를 비교하는 데만 씁니다.
- Anthropic의 1시간 규칙은 GPT 저작 기록의 호출 시간으로 정했습니다. Claude 모델의 응답 속도로 다시 재지 않았습니다.
- 기관 vLLM, MiniMax, Ollama의 캐시 설정은 보지 않았습니다.
- 수정 호출 방식의 품질 비교는 실제 수정 호출이 생긴 뒤에 해야 합니다.
