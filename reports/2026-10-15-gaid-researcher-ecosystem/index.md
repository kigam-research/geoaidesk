## 1. 요청한 것

> 사용자의 GAID와 Skill_hub의 구축 목표는 https://data.kigam.re.kr/ 과 동등한 수준의 지구과학 연구용 에이전트 프레임워크를 구축하고 싶은 것이다. 현재 구축한 시스템들은 비교적 목표를 도달하려고 했지만 여전히 신규 유입된 사람들과 코딩을 잘하는 연구자들의 입장에서 보았을 때에도 큰 이점이 없다고 생각한다. 현재 skill_hub는 스킬 및 워크플로우 레시피 제공 허브 플랫폼으로 수정개선되어야 할 필요가 있으며, GAID 시스템도 Workflow 기능이 UI/UX적으로 잘 활용될 수 있게 전면 수정될 필요가 있다고 생각한다. 단순한 채팅 에이전트 플랫폼의 경우에는 시간이 지날 수록 native codex, claude cli 시스템보다 나은점이 없어질 것이며, 현재 대시보드 시스템에서도 전반적으로 에이전트가 생각하는 방식의 디자인이다. 예를 들어서 GAID의 연구노트 시스템에서도 취지는 좋지만 보고된 근거, 결과파일 확인, SHA 대조 등과 같이 에이전트가 작업하기에 중요한 요소 위주로 노출되고 있으며, 사람 연구자가 중요하게 생각하는 결론이나 연구작업을 어떤 요청에 따라 어떤 흐름으로 수행했고, 어떤 결과가 나왔으며, 개선이나 제안점 또는 한계점, 더 나은 조사 방법, 관련 인터넷 자료, 논문 자료 등을 제공하는 방식과 같이 사람 연구자가 중요하게 생각하는 요소들이 연구노트에 정리되어야 한다. 그리고 시스템에 글자가 너무 많으며, 폰트도 작고 사람 연구자가 어디에 집중해야 할지도 불분명해진다. 사용자의 최종 목표는 https://data.kigam.re.kr/ 과 동등한 수준의 지구과학 연구용 에이전트 프레임워크를 구축하는 것이며, 연구자들이 해당 플랫폼에서 본인들의 연구 작업물들, 출판한 논문을 기반으로 스킬이나 워크플로우형 레시피를 작성하고 이것이 공유되는 생태계를 조성하여 KIGAM의 인공지능 생태계이자 기관 Second brain과 같은 역할을 하게 하고 싶다. 이러한 관점에서 연구자들이 유입될 수 있는 매력적인 기능 요소들이 있어야 하며, 연구자들은 코딩에 익숙하지 않기 때문에 스킬이나 워크플로우 레시피를 생성할 때 너무 많은 입력을 요구하게 해서는 안되며, 오히려 관련 문서나 본인들의 논문을 첨부하면, 에이전트가 분석 후 해당 문헌이나 자료들로부터 연구자와 함께 스킬 또는 워크플로우를 레시피를 생성할 수 있게 하는 필수 질문과 응답을 받아서 자동으로 생성해주는 기능도 필요하다. 에이전트는 확률적인 모델이므로 이를 위한 기반 코드와 시스템은 갖추어야 구현 가능할 것이라 판단한다. 사용자의 요청에 대해 심도있게 추론한 후에 현재 시스템의 현황과 어떤 방식으로 수정개선해나가고 추가적으로 어떤 것을 구현해야하는지를 함께 논의하고 작업해나가자. — 2026-10-15 요청

중간 피드백:

> 중간 피드백이다. 논문의 경우 현재는 대표 그림만 표시되고 있다. 일반 사용자들의 경우 PDF파일이나 링크를 제공하여 업로드할 것인데 바로 그림이 나오는 것은 인위적이다. PDF Viewer가 표시되는 것은 이해가 된다. 또는 pdf파일이 업로드되면 자동으로 k-dense-ai에서 제공하는 스킬이나 직접 구현하여 논문의 핵심을 분석하고 관련 그림들을 보여주는 방식도 가능할 것이다. 현재 방식은 사용자가 이미 구현해둔 pu 워크플로우 스킬의 내용을 모두 알고 있다는 상황으로 시안 및 설계를 진행하고 있는 것으로 보인다. 올바른 흐름은 pu 워크플로우 스킬이 없다는 상황을 가정하고 사용자가 관련 논문과 자료를 제공했을 때 자료를 분석한 후 에이전틱한 워크플로우 및 스킬을 생성하여 pu 워크플로우 스킬과 같이 만들어 보는 것이 올바른 절차이다. 그리고 k-dense-ai에서 제공하는 스킬들이나 BYOK에서 제공하는 workflow 레시피들이 어떻게 작동하는지 확인해보고 이용자들이 제공하는 자료로부터 어떻게 하면 해당 방식으로 만들 수 있는지를 고민하고 이것이 올바르게 시안 및 설계에도 반영될 수 있게해야한다. 하나의 참고 예시로는 notebooklm이 있을 수 있다. 완전히 동등한 구성은 아니지만 notebooklm에서는 사용자가 분석을 원하는 관련 자료를 입력하거나 URL을 제공하면 에이전트 해당 내용에 대해서 분석하고 Presentation이나 이미지나 보고서나 팟캐스트등을 생성하는 서비스이다. 스킬이나 workflow 레시피를 사용자들이 생성하는 흐름을 notebooklm의 자료처리 흐름에서 참고하라는 것이다. 그리고 이것이 GAID 프레임워크 시스템에서도 어떻게 연계될 것인지도 고려되어야 한다. — 2026-10-15 요청

이번 단계의 완료 기준은 현재 구현과 목표 사이의 차이를 근거로 설명하고, 재사용할 기반·새로 만들 기능·화면 구성·첫 실증의 순서를 제안하는 것입니다. 실제 제품 개편과 기관 서비스 배포는 아직 수행하지 않았습니다.

## 2. 수행한 것

1. GAID의 workflow 시작 과정, 연구노트의 기본 표시 순서, 결과·문헌·연구 메모리가 연결되는 방식을 코드에서 확인했습니다.
2. skill_hub의 방법 설명, 사례·시험 기록, 수동 제작 화면, 배포 및 비활성 기여 서비스가 제공하는 범위를 확인했습니다.
3. 지오빅데이터 오픈플랫폼과 WorkflowHub, Galaxy, protocols.io의 공식 자료를 비교했습니다. 계정 뒤의 제출·운영 동작은 시험하지 않았습니다.
4. 최신 21st.dev 템플릿과 shadcn/ui, 연결된 shadcnblocks의 후보를 조사했습니다. 일부 공개 데모는 실제 화면과 상호작용도 확인했습니다.
5. impeccable의 작업·읽기 화면 원칙, taste의 적용 범위, UUPM 검색 결과를 비교했습니다. 연구 작업에 맞지 않는 추천은 제외했습니다.
6. 사용자의 공간 PU 논문과 원고·원본 코드·자료·저장 결과를 찾았습니다. 초기 이미지 시안은 제작 시작 과정이 빠졌다는 피드백에 따라 제외했습니다.
7. K-Dense의 실제 스킬 파일, BYOK의 workflow 실행 경로, GAID의 PDF 처리·스킬 설치, skill_hub의 제작·제출 형식을 다시 확인했습니다. 기존 PU 스킬은 새 제작 과정의 입력에서 제외하고 나중에 비교할 기준으로만 둡니다.

## 3. 결과

### 3.1 목표를 판단할 기준

지오빅데이터 오픈플랫폼의 공식 안내에는 자료 발견·배포, 논문과 보고서, 데이터 인용, 시각화, 외부 프로그램의 자료 이용이 연결되어 있습니다. 기관 단위의 운영과 보존도 플랫폼의 역할에 포함됩니다. GAID와 skill_hub의 목표도 연구자가 자료와 방법을 발견하고, 사용 결과를 다시 기관의 지식으로 남기는 과정으로 평가해야 합니다. [KIGAM 소개](https://data.kigam.re.kr/about/info), [OpenAPI 안내](https://data.kigam.re.kr/guide/openapi).

역할은 다음과 같이 제안합니다. 두 제품의 화면을 통일하더라도 자료·실행·공유의 책임은 구분합니다.

| 영역 | 연구자가 얻어야 할 가치 | 우선 제공할 경험 |
|---|---|---|
| skill_hub | 내 문제에 쓸 방법과 그 방법을 사용한 사람·사례를 찾음 | 질문·자료·예상 결과로 검색, 대표 결과와 적용 조건 확인, 샘플과 내 자료로 실행 |
| GAID | 자료를 넣고 방법을 선택해 결과와 다음 판단을 얻음 | 자료 확인, 필요한 질문, 실행 상태, 결과 비교, 연구노트, 방법으로 저장 |
| 기관 공통 기반 | 동료의 연구를 다시 찾고 이어서 사용함 | 계정·연구팀·공유 범위, 출처·버전·기여, 실행 환경, 검색과 변경 이력 |

기존 지오빅데이터 서비스를 새로 만드는 범위로 확대하지 않습니다. 자료 식별자와 허용된 API를 연결해, 자료를 가져온 뒤 어떤 방법으로 연구했는지를 이어 붙이는 방향입니다.

신규 연구자는 설정과 코딩을 줄이고 첫 결과를 얻을 수 있어야 합니다. 코딩 연구자는 기존 스크립트를 그대로 활용하면서 동료의 방법·환경·시험 사례를 가져오고 자기 기여를 인용받을 수 있어야 합니다. 동일한 방법 묶음을 GAID와 터미널에서 실행할 수 있도록 설계하면, 익숙한 코딩 도구를 포기할 필요가 없습니다. Galaxy는 방법 정의와 실행별 자료·매개변수를 분리해 명령줄 실행을 안내합니다. GAID에서도 이 분리를 참고할 수 있습니다. [Galaxy workflow 자동 실행 안내](https://training.galaxyproject.org/training-material/topics/galaxy-interface/tutorials/workflow-automation/tutorial.html).

### 3.2 현재 구현에서 확인한 차이

| 현재 기반 | 확인한 제약 | 개편 방향 |
|---|---|---|
| Workflow 목록, 자료 선택, 과학적 선택 항목 | 선택값이 대화 초안으로 합쳐집니다. 해당 선택과 실행·단계·결과를 묶는 연구 단위가 없습니다. | 선택한 방법과 조건을 구조화해 보관하고 실제 실행에 연결합니다. |
| 가설·방법·관찰·결정·한계가 있는 연구노트 | 기본 프로젝트 보기는 시간순입니다. 이야기 보기도 질문별 연결보다 항목 종류별 묶음입니다. | 연구 질문별로 현재 결론, 대표 결과, 수행 흐름과 다음 판단을 보여줍니다. |
| 결과 카드, 원자료 추적, 파일 대조 | 일부 화면은 결과 제목보다 내부 식별자와 파일 대조 정보를 먼저 보여줍니다. | 결과 제목·그림을 먼저 놓고 상세 기록은 필요할 때 엽니다. 중요한 누락·변경 경고는 결과 옆에 남깁니다. |
| 프로젝트 연구 메모리와 문헌 카드 | 연구 메모리는 프로젝트의 노트·계획을 검색합니다. 문헌 전체나 기관의 연구를 통합 검색하는 기능은 아닙니다. | 원문·논문·방법·결과를 연결하고, 공유 권한에 맞는 범위부터 검색합니다. |
| skill_hub의 방법·사례·버전·배포 기반 | 제작 화면은 연구자가 방법을 직접 입력합니다. 논문을 읽어 방법과 실행 코드를 만드는 기능은 없습니다. | 문헌·코드·기존 결과를 읽고 방법 초안과 필수 질문을 만드는 공동 제작 기능을 더합니다. |
| 준비된 기여·심사 서비스 | 비활성 상태이며 현재 공개 사이트와 준비된 새 사이트가 다릅니다. | 기존 기반의 재사용 여부를 확인하고, 연구자 계정과 지속 가능한 기여 경로를 연결합니다. |

기존 앱에는 특정 견고성 시험을 위한 원격 실행이 있습니다. 새로 필요한 것은 일반 catalogue workflow와 연구자 제작 레시피를 연구 작업의 시작부터 결과까지 연결하는 구조입니다.

### 3.3 연구자가 따라갈 세 가지 경로

**방법을 찾아 내 자료에 적용합니다.** 연구 목적이나 파일을 넣으면 적용 가능한 방법을 보여줍니다. 방법 상세에서는 결과 예시, 필요한 자료, 적용 조건, 실제 시험 범위를 확인합니다. 샘플을 먼저 살펴보거나 자기 자료로 시작할 수 있습니다. 파일에서 확인할 수 있는 형식·단위·범위는 채우고, 과학적 판단이 필요한 차이만 묻습니다.

**논문과 작업물로 방법을 만듭니다.** 연구자는 논문, 코드, 기존 결과를 첨부하고 재사용하려는 작업을 짧게 설명합니다. 에이전트는 해당 근거에서 입력, 방법 단계, 판단 기준, 계산 코드, 출력과 한계를 추출합니다. 원문에 있는 내용, 코드에 있는 내용, 에이전트가 제안한 보완, 모르는 내용을 구분합니다. 연구자는 원문과 방법 초안을 나란히 보며 빠진 조건만 답합니다. 기존 코드가 있으면 먼저 감싸서 재사용하고, 없는 부분만 생성합니다.

**수행한 연구를 다시 사용하고 공유합니다.** 실행이 끝나면 질문에 대한 답, 결과 그림·표, 사용한 방법과 주요 선택, 한계, 다음 조사 제안과 관련 문헌을 연구노트에 남깁니다. 다른 자료로 재실행하거나, 개인 자료를 제외한 방법 묶음을 공유할 수 있습니다. 다른 연구자의 적용 결과와 수정 사항은 사용한 방법의 버전에 연결합니다.

모든 논문을 즉시 실행 가능한 분석으로 바꾸지는 않습니다. 현장 조사·실험 절차·해석 지침은 설명형 스킬이나 사람이 수행하는 단계로 남을 수 있습니다. 계산 가능한 부분과 사람의 판단이 필요한 부분을 구분하는 것이 제작 과정의 일부입니다.

### 3.4 연구노트의 기본 화면

노트의 기본 단위는 연구 질문으로 제안합니다. 하나의 질문에 여러 대화와 실행이 이어질 수 있습니다.

기본 읽기 순서는 다음과 같습니다.

1. **현재 결론과 미해결 부분.** 무엇을 알게 되었고 어디까지 적용할 수 있는지 먼저 읽습니다.
2. **대표 결과.** 제목이 붙은 그림·표에서 원자료와 비교 결과로 이동합니다.
3. **수행한 흐름과 선택 이유.** 원래 요청, 사용한 방법, 중요한 변경과 판단을 연결합니다.
4. **한계와 다음 조사.** 결과가 달라질 조건, 필요한 추가 자료, 비교할 대안을 보여줍니다.
5. **관련 문헌과 상세 기록.** 각 자료를 왜 썼는지 표시하고, 원문 위치·코드·실행 기록을 엽니다.

에이전트가 기록을 읽고 해석 초안을 작성할 수는 있지만, 결과 수치나 수행 사실을 새로 지어내서는 안 됩니다. 관찰은 실제 결과에 연결하고, 해석과 후속 제안은 별도로 저장합니다. 기존 기록에서 질문과 결론을 확정할 수 없으면 미분류 상태로 남겨 연구자가 묶을 수 있게 합니다.

화면은 한 번에 읽을 내용을 줄이고 본문과 조작 요소의 크기를 구분합니다. 시작 기준으로 본문은 16–18px 수준에서 검토하되, 실제 한글 문장과 연구자의 화면에서 확인해야 합니다. 글자를 키운 채 모든 정보를 그대로 펼치는 방식은 피합니다. 표·코드가 필요한 숙련자는 상세 보기에서 충분한 밀도로 작업할 수 있어야 합니다.

### 3.5 확률적인 모델을 받쳐 줄 시스템

| 시스템이 보관할 것 | 모델에만 맡길 때 생기는 문제 | 필요한 처리 |
|---|---|---|
| 연구 질문과 실제 요청 | 서로 다른 질문이나 시스템 알림이 하나의 연구로 섞임 | 요청·연구 단위·대화·실행을 명시적으로 연결 |
| 문헌 근거와 미상 항목 | 논문에 없는 조건을 원문에 있던 것처럼 설명 | 페이지·절·코드 위치 연결, 원문·연구자 답·제안·미상 구분 |
| 방법의 특정 버전 | 같은 이름의 방법이 실행 때마다 바뀜 | 코드·입출력·매개변수·환경·시험 조건을 묶어 고정 |
| 실제 실행과 검사 | 에이전트가 “완료”라고 말하면 성공으로 표시 | 실행기가 종료·출력·검사 결과를 기록하고 화면 상태를 계산 |
| 연구자의 해석과 수정 | 최신 요약이 앞선 결과와 이견을 덮어씀 | 출처가 연결된 해석 개정과 변경 이유 보관 |
| 공유 범위와 기여 | 개인 입력 자료가 방법 공개와 함께 유출되거나 저자 기여가 사라짐 | 공유할 묶음을 미리 보여주고 원저자·구현자·시험자와 버전 연결 |

검사에는 단계가 있습니다. 파일과 항목이 갖춰졌는지, 단위와 자료 조건이 맞는지, 기준 결과와 수치가 일치하는지, 다른 자료에 적용했을 때 과학적으로 적합한지를 구분합니다. 샘플 기대값과 허용오차는 시험 전에 정하고, 생성된 결과에 맞춰 바꾸지 않습니다. 프로그램이 끝났다는 상태와 연구자가 해석을 검토했다는 상태는 별개입니다.

레시피는 설명문에 더해 실행 코드, 입력·매개변수 규칙, 환경, 출력, 샘플과 검사 조건을 담아야 합니다. 특정 PC의 경로나 자격증명은 넣지 않고, 실행 위치별 자료·환경·인증 설정을 별도로 연결합니다. 현재의 “시작 설정 저장”과 실행 레시피는 구분해야 합니다. 기존 형식의 뜻을 유지하면서 새 연결 규약을 설계합니다. 큰 범용 workflow 편집기보다 첫 사례가 요구하는 단계와 실행 상태를 먼저 구현하는 편이 적절합니다.

### 3.6 기관 웹을 기본으로 할 때 달라지는 범위

기관 웹은 계정과 연구팀, 개인·팀·기관 공유 범위, 지속적인 초안 저장, 연구자별 자료 공간을 제공해야 합니다. 실행은 작업별 환경에서 수행하고, 오래 걸리는 작업도 연결이 끊긴 뒤 확인할 수 있어야 합니다. 작업 취소와 자원 사용도 실행 기록에 남겨야 합니다.

기관 실행기는 연구자별 자료 접근과 실행 환경을 분리해야 합니다. 서버 공용 자격증명과 다른 연구자의 자료가 각 작업에 노출되지 않도록 설계해야 합니다.

현재 검토용 GAID를 여러 사람이 함께 쓰도록 주소만 공개하는 것으로 이 목표를 충족할 수 없습니다. 기존 앱의 실행 기능을 재사용하되, 기관 계정·저장·작업 실행 경계를 설계해야 합니다. 기관 인증 방식과 가용 연산 자원은 아직 확인하지 않았습니다.

로컬 실행은 같은 방법 버전과 실행 조건을 사용하는 선택지로 둡니다. 로컬에 남길 자료와 기관에 돌려줄 결과·요약을 구분해야 합니다. 기관의 연구 메모리도 개인 대화를 전부 모으는 방식보다, 공유된 연구 질문·방법·결과·수정과 해당 출처를 먼저 연결하는 편이 목적에 맞습니다.

### 3.7 화면 구조와 컴포넌트 선정 근거

연구 작업 화면은 실행 중심으로, 연구노트와 방법 상세는 읽기와 판단 중심으로 설계합니다. 디자인 도구의 추천은 실제 작업에 맞는지 확인한 뒤 사용합니다.

| 확인한 후보 | 채택할 부분 | 그대로 사용하지 않을 부분 |

공동 제작 화면은 **원문·코드·기존 결과를 보는 영역과 수정 가능한 방법 초안을 나란히 놓는 구성**을 권합니다. 근거를 선택하면 관련 방법 단계가 드러나고, 빠진 결정은 해당 단계에서 답합니다. 이 조합은 위 후보의 상호작용을 바탕으로 새로 설계할 부분이며, 구매 블록에 이미 완성되어 있는 기능은 아닙니다.

AI CRM과 AdminCN, 사례 설명 템플릿은 공개 데모를 직접 확인했습니다. shadcnblocks는 연결된 MCP에서 두 항목을 직접 조회하고, 공식 미리보기 구조와 제공 스크린샷을 확인했습니다. 전체 화면 미리보기는 로그인이 필요해 상호작용을 시험하지 않았습니다. Orbit Mail은 실제 데모를 확인하지 못해 선정 근거에서 제외했습니다.

UUPM의 첫 검색은 기관 소개·포트폴리오 구성을 추천해 제외했습니다. 범위를 좁힌 검색에서 방법 탐색과 버전 전환, 입력 검사의 참고점을 얻었지만 이를 완성된 디자인 시스템으로 채택하지 않았습니다. taste는 대시보드와 다단계 입력 화면을 적용 범위에서 제외하므로, 허브의 소개·방법 설명 화면에 한정합니다. GAID 작업 화면에는 impeccable의 작업·읽기 원칙을 우선합니다.

초기 A/B/C 이미지는 대표 지도와 이미 채워진 방법을 먼저 보여 줬습니다. 사용자의 피드백에 따라 이 시안은 선택지에서 제외했습니다. 다음 시안은 자료 입력·원문 보기, 분석 내용과 질문, 생성된 방법과 GAID 시험을 이어서 보여줘야 합니다. 원문·초안을 나란히 보는 구성은 분석이 끝난 뒤에 사용합니다.

### 3.8 논문을 처음 받은 상태에서 시작하는 제작 과정

공간 PU 스킬이 없다고 가정합니다. 연구자가 제공한 논문·자료에서 방법을 만드는 과정이 첫 실증입니다. 기존 스킬의 설명과 코드를 생성 입력에 넣으면, 논문에서 방법을 만드는 능력을 확인할 수 없습니다.

| 단계 | 연구자가 보는 것과 하는 일 | 시스템이 남겨야 할 근거 |
|---|---|---|
| 자료 입력 | PDF 업로드 또는 논문 URL·DOI 입력. 코드·자료·기존 결과는 있으면 첨부합니다. | 실제 받은 자료, 접근 범위와 원본 위치 |
| 원문 확인·분석 | 원문 PDF를 보고, 논문에서 어떤 작업을 방법으로 만들지 짧게 설명합니다. 자료를 받으면 분석을 시작할 수 있습니다. | 본문·그림을 읽은 범위, 추출 산출물, 읽지 못한 부분 |
| 내용 이해 | 연구 질문, 사용 자료, 방법, 관련 그림, 한계를 확인합니다. 근거를 누르면 원문 페이지나 코드로 이동합니다. | 추출한 사실과 에이전트의 해석, 실제 페이지·그림·코드 위치 |
| 필요한 질문 | 원문으로 알 수 없고 재사용 방식에 영향을 주는 선택만 답합니다. | 연구자의 답, 미답 항목과 그 항목이 필요한 이유 |
| 방법 생성 | 사용 조건·입력·단계·예상 결과를 읽고 수정합니다. 스킬과 workflow 시작 요청을 생성합니다. | 실제 생성 파일, 연결한 근거, 구현 여부와 미시험 항목 |
| GAID 시험·수정 | 개인 초안을 시험하고 결과를 확인합니다. 문제가 있으면 같은 초안으로 돌아가 수정합니다. | 사용한 방법·자료 버전, 실행 결과와 검사 기록 |
| 재사용·공유 | 내 자료에 적용하거나, 공유할 방법과 사례를 선택합니다. | 방법 버전, 적용 사례와 기여, 공유 범위 |

처음에는 파일 이름과 원문만 보여줍니다. 논문 제목을 인식했다고 핵심 분석까지 끝난 것으로 표시하지 않습니다. URL로 초록만 읽었다면 접근 범위를 그대로 표시합니다. 그림은 실제로 추출하고 관련성을 판단한 뒤 캡션·페이지와 함께 보여줍니다. 과학 그림은 원본에서 추출하며 이미지 생성 모델로 다시 그리지 않습니다.

질문도 분석 결과에 따라 달라져야 합니다. 원문과 코드에 격자 크기나 모델 설정이 있으면 다시 입력받지 않습니다. 재현이 목적인지 다른 자료에 적용할 방법을 만드는지, 결과를 어떤 판단에 쓸지처럼 작업을 바꾸는 차이만 묻습니다. 답하지 않은 중요한 조건은 미정으로 남깁니다.

NotebookLM은 사용자가 자료를 먼저 넣고 그 자료에서 산출물을 만드는 흐름의 참고입니다. 공식 자료에서 확인할 범위는 자료 처리와 출처 확인, 산출물 생성 과정입니다. 계산 코드의 실행·검사와 재사용 가능한 방법 묶음은 GAID에서 별도로 설계해야 합니다.

### 3.9 생성할 스킬과 workflow는 실제로 무엇인가

| 현재 형식 | 실제 작동 방식 | 새 제작 기능에서 만들 것 |
|---|---|---|
| K-Dense/Pi 스킬 | `SKILL.md`의 설명으로 사용 대상을 찾고, 지침을 읽어 일반 도구를 사용합니다. 코드·참고자료를 함께 담을 수 있습니다. | 적용 조건, 과학적 절차, 입출력·한계, 필요한 코드와 참고자료가 있는 실제 스킬 폴더 |
| BYOK workflow | 정해진 요청문에 입력값과 자료 경로를 넣어 대화로 보냅니다. 단계 문장이 자동 실행 노드를 뜻하지는 않습니다. | 새 스킬을 호출하고 입력·선택을 전달하는 시작 요청. 필요한 계산은 실제 코드가 수행 |
| Prompt template | 저장한 요청문을 명령과 인자로 다시 사용합니다. | 새 스킬과 함께 사용할 재사용 가능한 요청문 |
| 현재 GAID `.geo-start.json` | 이미 목록에 등록된 workflow와 스킬을 참조하는 시작 설정입니다. | 기존 형식은 유지. 새 개인 방법은 별도 등록 경로를 추가 |
| skill_hub 제출 묶음 | `SKILL.md`, `atlas.yaml`, `LICENSE`와 관련 파일을 제출합니다. | 연구자가 읽고 고친 초안에서 시스템이 메타데이터·배포 파일을 생성 |

현재 GAID는 새 스킬을 설치하고 명시적으로 호출할 수 있습니다. 그러나 `.geo-start.json`에 새로운 이름을 넣는 것만으로 새 workflow를 만들 수는 없습니다. 목록의 스킬·workflow 식별자가 실제로 존재하는지 검사하기 때문입니다. 새 개인 방법을 workflow 화면에서 시작할 수 있게 하는 등록 기능이 필요합니다.

K-Dense의 로컬 고정 자료에는 `markitdown`의 문서 변환과 처리 기록, `scientific-writing`의 출처 목록·주장 대조 양식이 있습니다. 재사용 후보이지만 현재 GAID의 13개 스킬 목록에는 포함되지 않았습니다. Markdown 변환만으로 정확한 그림·캡션·페이지 위치가 확보되지도 않습니다. 읽기·질문·방법 작성에는 스킬을 활용합니다. 원문 보관·페이지 추출·파일 생성·상태 기록은 프로그램이 담당하도록 제안합니다.

논문만 있고 코드가 없다면 설명형 스킬부터 만들 수 있습니다. 계산 코드를 생성하는 경우에는 그 작업과 시험 상태를 따로 보여줘야 합니다. 스킬 파일 생성과 실행 가능한 분석의 완성을 구분합니다.

### 3.10 GAID와 허브를 연결할 최소 구조

| 재사용할 기반 | 추가할 연결 |
|---|---|
| GAID 파일 업로드·PDF 뷰어·주석 | 자료 수집 상태, 실제 페이지·그림 추출 기록, 분석 내용에서 원문으로 이동 |
| 질문 도구와 연구 기록 | 원문으로 해결되지 않은 질문·답을 방법 초안에 저장. 대화나 서버 연결이 끝나도 초안 유지 |
| 스킬 미리보기·설치·호출 | 생성한 다중 파일 초안을 설치 경로에 연결하고 개인 방법으로 등록 |
| 실행·결과·연구노트 | 정확한 방법·입력 버전으로 시험하고, 결과와 수정 사항을 초안에 연결 |
| skill_hub 제작·제출·패키지 | 검토한 초안을 제출 형식으로 변환하고, 공유할 자료만 묶어 배포 |

기관 웹에서 시작한 작업은 같은 자료와 초안을 유지한 채 GAID의 시험 화면으로 이어져야 합니다. 사용자가 다른 사이트로 이동하며 PDF를 다시 올리거나 과학적 선택을 다시 입력하게 해서는 안 됩니다. GAID에서 시작한 작업도 같은 제작 서비스를 사용하고, 허브는 방법 발견·기여·공유의 입구로 둡니다.

개인 초안의 시험은 허브 공개보다 먼저 가능해야 합니다. 허브의 현재 기여 서비스는 비활성 상태이며, 스킬 제출과 workflow 목록 갱신의 저장 위치도 다릅니다. 현재 새 스킬 제출만으로 workflow 카드까지 자동 공개되지는 않습니다. 이 연결은 별도 구현 범위입니다.

첫 실증에서는 제공된 원문·원본 코드·자료 설명·기존 결과만 생성 입력으로 고정합니다. 이미 만든 PU 스킬과 일반화된 도우미 코드는 제외합니다. 초안을 만든 뒤 기존 스킬과 비교하되, 문장이 비슷한지보다 출처에 맞는 방법인지, 필요한 질문을 했는지, 생성한 파일을 GAID에서 불러 실제로 사용할 수 있는지 확인합니다.

발표 논문의 5km 격자·50km 평가 블록과 Atlas의 40km 축약 사례는 구분합니다. 후자는 독립된 새 자료의 적용 사례가 아닙니다. 다른 연구자의 자료에 적용하는 후속 시험에는 별도의 입력 자료가 필요합니다.

### 3.11 구현 순서와 완료 기준

| 단계 | 만들거나 정할 것 | 다음 단계로 넘어갈 근거 |
|---|---|---|
| 1. 자료에서 방법을 만드는 화면 설계 | PU 스킬 없이 논문·자료 입력부터 시작. 원문·분석·질문·생성·시험 화면 설계 | 대표 그림이 갑자기 나타나지 않고, 연구자가 자료에서 방법이 만들어지는 흐름을 이해함 |
| 2. 자료 분석과 초안의 최소 기반 | 원본 보관, 페이지·그림 추출, 근거가 연결된 방법 초안과 질문·답 저장 | 제공한 자료에서 초안의 근거를 다시 찾고, 연결이 끊긴 뒤에도 이어서 작업 |
| 3. 논문 기반 공동 제작과 재사용 | 출처가 있는 방법 추출, 필수 질문, 스킬·시작 요청 생성, 개인 방법 등록·시험, 다른 자료 적용 | 기존 PU 스킬 없이 만든 방법을 GAID에서 사용. 두 번째 연구자는 결과를 얻거나 적용 불가 이유를 확인 |
| 4. 기관 서비스와 허브 공유 | 계정·작업공간·실행 격리, 버전·기여·사례·검색, 제한 공유와 수정·실패 사례 환류 | 사용자별 자료를 구분하고, 공유된 방법의 사용·변경·인용을 원 방법에 연결 |

단계 1에서 공통 데이터 구조를 정한 뒤에는 자료 처리, 새 방법 등록, 화면을 나누어 만들 수 있습니다. 지질 파일 보기, 노트·결과 저장, 기존 코드, 배포 묶음과 기여 심사는 필요한 부분을 재사용합니다. 기관의 여러 연구자가 함께 쓰는 배포는 계정·자료·실행 격리를 갖춘 뒤에 합니다.

첫 실증은 소수의 실제 연구 사례로 시작합니다. 방법 관리자를 정하고, 생성한 스킬의 개수보다 다른 연구자의 재사용 결과를 평가합니다. WorkflowHub가 팀·관리자·컬렉션과 버전·기여를 다루는 방식은 이 운영 설계의 참고가 됩니다. [WorkflowHub 공식 안내](https://about.workflowhub.eu/docs/guide-to-using-workflowhub/).

측정할 항목은 최초 유효 결과까지 걸린 시간, 연구자가 답한 질문과 수동 수정량, 원저자에게 다시 물은 횟수, 다른 자료에서 검사한 결과, 실패·미상 조건의 누락 여부입니다. 목표 수치는 첫 사례와 현재 수행 방식을 측정한 뒤 정합니다.

## 4. 검증

- 제품 현황: workflow 시작, notebook의 프로젝트·이야기 보기, 결과 링크, 연구 메모리, skill_hub 제작·배포 계약을 코드와 문서로 대조했습니다. 없는 기능과 이미 있는 기능을 구분했습니다.
- 수정된 제작 흐름: 실제 upstream 기준의 요청문 workflow와 스킬 생성 경로, 현재 `.geo-start.json` 검증 규칙, PDF 뷰어와 페이지 추출의 차이, 허브 제출 형식을 확인했습니다. 자동 제작이나 분석 서비스를 실행한 시험은 아닙니다.
- 외부 근거: 공식 자료를 읽고 공개 데모의 일부 화면을 확인했습니다. 템플릿 설명, 화면 관찰, 제안한 조합을 구분했습니다. 계정 뒤 기능과 기관 운영 성능은 확인하지 않았습니다.
- 과학적 검증: 해당 없음. 이번 단계에서 자료를 분석하거나 모델 과제를 새로 실행하지 않았습니다.
- 소프트웨어 검증: 제품 코드를 바꾸지 않아 전체 자동 검사는 실행하지 않았습니다. UUPM 검색 도구 실행은 제품 검사나 연구자 사용성 시험이 아닙니다.

## 5. 한계

- 공간 PU 논문과 관련 원고·원본 코드·자료·저장 결과는 찾았습니다. 기존 스킬 없이 자료에서 새 스킬을 생성하는 실증, 원문 페이지·그림 추출 시험과 새 분석 실행은 아직 하지 않았습니다. 다른 연구자의 적용 자료도 미정입니다.
- 기관 계정 연동, 배포 위치, 연산 자원과 운영 담당은 미확인입니다. 구현 일정과 비용을 산정하지 않았습니다.
- 현재 증거는 코드와 기존 시험, 공식 문서, 일부 화면 확인입니다. 신규 연구자와 코딩 연구자의 실제 사용 결과는 아직 없습니다.
- 준비된 skill_hub 사이트와 실제 공개본은 다릅니다. 기관 브랜드 승인과 공개 배포는 이번 설계 논의와 별도로 유지합니다.
- 추천한 화면 구조는 연구자와 실제 자료로 확인해야 합니다. 라이브러리나 디자인 스킬을 사용했다는 사실만으로 사용성이 증명되지는 않습니다.

## 6. 결정할 일

기관 웹 우선·로컬 실행 선택, 공간 PU 논문 사례, 이미지 우선 제작을 반영했습니다. 논문을 다시 선정할 필요는 없습니다.

지금은 사용자의 중간 피드백에 따라 자료 입력부터 시작하는 화면을 다시 설계하고 있습니다. NotebookLM 공식 자료 조사와 현재 코드의 연결 조건을 반영한 뒤 새 시안을 제시합니다. 기존 A/B/C안 중 하나를 고르는 단계가 아닙니다. 인증·운영 방식과 다른 연구자의 적용 자료는 후속 실증 범위에서 정합니다.
